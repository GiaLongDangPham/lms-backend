# Bug-06, Bug-08, and Bug-09 Backend Design

**Date:** 21/11/2026  
**Owner:** Nam  
**Status:** Proposed

## Intent

Make the backend the source of truth for whether a student may submit, expose the
teacher who graded a published result, and return self-contained notifications plus
an unread aggregate. These changes support the F3, F4, and F5 fixes without exposing
Draft grade data or changing submission/publication invariants.

## Goals

- Return submission capability on every student Assignment DTO, including when no
  Submission row exists.
- Report an automatic-zero result as `GRADED`, not `NOT_SUBMITTED`, in
  `mySubmissionStatus`.
- Add `gradedBy` to the student-safe PublishedGrade response while preserving
  `publishedBy` as the distinct publication actor.
- Include assignment, class, and Vietnam-time deadline context in assignment and
  deadline notifications, and include the assignment title in result notifications.
- Add `unreadCount` to NotificationPage so F5 can render a menu badge without loading
  every notification page.
- Keep all additions backward compatible and update the OpenAPI contract and tests.

## Non-goals

- Do not return a synthetic Submission when the student has never submitted.
- Do not weaken the POST submission transaction or change its stable error codes.
- Do not renumber immutable grade-history revisions. F4 will label the filtered
  Published entries by display order instead of presenting revision as publication count.
- Do not implement the frontend button, translation, history label, or menu badge changes.
- Do not add a migration or backfill previously stored notification text.

## Existing constraints

- A first submission may be late; deadline expiry only locks a later version.
- Any grade or assignment-wide publication permanently locks submission.
- PublishedGrade must remain student-safe and must never reveal Draft score or feedback.
- Notification text is an event-time snapshot. Existing notification rows remain unchanged.
- PostgreSQL owns deadline comparisons and notification timestamps.

## Approaches

### 1. Minimal existing-contract patch

Fix `mySubmissionStatus`, add `gradedBy`, and enrich notification text. This leaves F3
to infer capability from multiple resources and leaves F5 loading all notification pages
to count unread rows.

### 2. Backward-compatible contract additions — selected

In addition to the minimal patch, add student-only `canSubmit` and `lockedReason` fields
to Assignment and add `unreadCount` to NotificationPage. Existing clients ignore the new
properties, while new clients receive explicit server-owned state even without a
Submission row.

### 3. Synthetic submission or a new state endpoint

A synthetic Submission misrepresents persistence and requires nullable identifiers. A new
endpoint duplicates assignment authorization and paging consumers for one small state
projection. Both add more complexity than extending the existing Assignment DTO.

## API behavior

### Student Assignment capability

Every Assignment returned to a student includes:

- `canSubmit: false`, `lockedReason: "GRADED"`, and
  `mySubmissionStatus: "GRADED"` when that enrollment has any grade, including
  `AUTO_ZERO_NO_SUBMISSION`.
- `canSubmit: false` and `lockedReason: "GRADED"` when assignment-wide publication is
  recorded, even if inconsistent legacy data is missing the expected grade.
- `canSubmit: false` and `lockedReason: "DEADLINE_PASSED"` only when a Submission already
  has a version and the current assignment deadline has passed.
- `canSubmit: true` and `lockedReason: null` for a first submission, including after the
  deadline, and for a resubmission before or exactly at the deadline.

Teacher Assignment DTOs do not gain these student-specific properties. Submission DTO
behavior remains unchanged.

### Published result actor

PublishedGrade adds required `gradedBy: UserSummary`. `publishedBy` remains required and
may identify a different teacher. For `AUTO_ZERO_NO_SUBMISSION`, `gradedBy` is the teacher
recorded by the existing automatic-zero transaction.

### Notification content and count

New event snapshots use these facts:

- `ASSIGNMENT_CREATED`: assignment title, class name, and deadline formatted as
  `HH:mm DD/MM/YYYY (giờ Việt Nam)` using the `Asia/Ho_Chi_Minh` timezone.
- `DEADLINE_REMINDER`: assignment title, class name, and the same exact deadline format.
- `GRADE_PUBLISHED`: assignment title; no score or feedback.

NotificationPage adds required `unreadCount`, the total unread rows for the authenticated
student across the whole inbox, independent of cursor and limit. Mark-read responses stay
unchanged. The count may reflect a neighboring committed transaction before or after the
page query; no cross-query snapshot guarantee is introduced.

## Testing

- Assignment integration coverage pins automatic-zero capability, first-late submission,
  resubmission deadline locking, and publication locking.
- Assessment integration and contract tests require `gradedBy` on student results and keep
  Draft fields private.
- Notification integration tests assert new Vietnamese snapshot context, Vietnam-time
  formatting, result title inclusion, and unread counts independent of pagination/read state.
- Run focused tests first, then lint, typecheck, unit/contract tests, build, database tests,
  and the complete API integration suite where PostgreSQL is available.
