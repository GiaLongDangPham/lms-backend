# Bug-06, Bug-08, and Bug-09 Backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make submission capability, published grader identity, notification context, and unread totals explicit in the backend contract.

**Architecture:** Extend the existing Assignment and NotificationPage DTOs without creating endpoints or migrations. Keep state calculation in assignment service/repository, student-safe grade mapping in assessment service, and notification snapshot/count SQL in the notification repository.

**Tech Stack:** Node.js 22, Express 5, TypeScript ESM, PostgreSQL 17, pg, Vitest/Supertest/Ajv, OpenAPI 3.1

**Spec:** `docs/superpowers/specs/2026-11-21-bugs-06-08-09-be-design.md`

## Global Constraints

- Preserve the 48 existing operations; additions are response fields, not new endpoints.
- A first submission remains allowed after deadline; only a later version is deadline-locked.
- Grade/publication locks remain enforced transactionally by POST submission.
- Never expose Draft score/feedback or conflate `gradedBy` with `publishedBy`.
- Format notification deadlines with PostgreSQL `Asia/Ho_Chi_Minh`; do not use process-local time.
- Do not add a migration or rewrite existing notification rows.

## Review Focus

- Automatic zero without a Submission must be `GRADED`, `canSubmit: false`, and `lockedReason: GRADED`.
- A first submission after deadline must remain allowed, while an existing submission after deadline is locked.
- Different grading and publishing teachers must survive in `gradedBy` and `publishedBy` respectively.
- Notification bodies must remain student-safe and quote class/assignment titles without SQL interpolation.
- `unreadCount` must cover the whole recipient inbox and remain independent of pagination cursor/limit.
